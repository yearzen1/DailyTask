# 布局与间距（Layout & Spacing）

## 留白

- 默认给足。留白不够是最常见的问题，也是让界面显"廉价"的头号原因。
- **减少留白是需要理由的决定**，加留白不需要。信号不对称：拥挤一眼能看出，空旷很少是问题。
- 紧凑界面有正当场景（数据表格、交易终端、IDE），但那时是刻意选择，不是默认结果。

## 间距/尺寸体系

### 为什么 4px 倍数不够

一像素一像素地试随手编的值，会让你在 120 和 125 之间反复横跳。真正可用的体系要求**相邻取值的相对差**足够明显：

- 12 → 16 是 +33%，肉眼明显；
- 500 → 520 是 +4%，几乎看不出来。

所以：**相邻档差距 ≥ 25%**，小端密、大端疏。

### 阶梯

```
4 · 8 · 12 · 16 · 24 · 32 · 48 · 64 · 96 · 128 · 192 · 256 · 384 · 512 · 640 · 768
```

- 16px 是好的基准：整除干净，且是浏览器默认字号。
- 所有 margin / padding / gap / width / height 只从阶梯取值。
- 用法：需要一个值 → 取一个 → 不够 → 取下一档。永不手编 18、28、36。

### 元素内部的比例关系

组件内部各项属性（内边距、圆角、字号、图标尺寸）不必按固定比例联动。按钮 16px 字号配 16px 左右内边距没有问题；把整组数值按 1.5 倍等比放大反而会得到怪比例。**每个属性独立从阶梯取**。

## 画布：别填满屏幕

- 有 1440px 不代表要用 1440px。只需要 600px 就用 600px，边缘留白不会害人。
- 通栏不该传染：导航通栏，不等于每个区块都通栏。给每个元素它刚好需要的空间。
- 发现小界面在大画布上难设计 → **把画布缩小**。响应式项目从 ~400px 开始设计移动端，再往上扩，需要改的比想象中少。
- 窄内容放不进宽界面 → **拆成分栏**（说明文字一栏、表单一栏），而不是把表单拉宽。
- 也别反过来硬塞：真需要大空间就用。

## 栅格：工具，不是宗教

- 栅格提供的是弹性百分比宽度。它有用，但把所有布局决定外包给栅格会出问题。
- **侧边栏**：给固定宽度（按内容优化），主内容区弹性填满剩余，内部再套自己的栅格。用 25%/75% 的弹性比例会让侧边栏在大屏浪费空间、在小屏压到不可用。
- **组件内部**：除非真的希望它跟着缩放，否则不要用百分比定尺寸。
- **永远别为了"对齐栅格"而缩小元素**。知道卡片最佳宽度是 500px，就给它 `max-width: 500px`，只在屏幕更窄时才缩小；用栅格列宽会出现"中等屏幕比大屏更宽"的荒唐区间。

## 相对尺寸无法通用

- 试图把"标题 = 正文 × 2.5"这类关系固化成 `em`，会在小屏崩掉：正文 14px 时标题 35px 明显过大，实际合适的是 20–24px（1.5–1.7 倍）。
- 规律：**大屏上大的元素，到小屏要缩得更快**；小元素与大元素的差距在小屏应该收窄。
- 所以断点处直接给绝对值，不要靠相对单位继承。

## 避免含糊的间距（proximity）

- 分组靠距离，不靠线。组内间距 < 组间间距，且差距要肉眼可辨（例如组内 8/12，组间 32/48）。
- 间距相近但不相等（16 vs 20）时，读者既看不出分组，又觉得哪里不对——这是"说不出的丑"的常见来源。
- 想要更明确的分组时，优先加大间距，其次换背景色，最后才加分割线或边框。

## 自检

- 是否存在阶梯外的数值（5、10、13、18、20、28、36、44）？
- 页面在 1440px 下是否被迫拉伸了本该更窄的内容？
- 侧边栏宽度是否随屏幕变化？
- 去掉所有边框后，分组是否还能靠间距读出来？
